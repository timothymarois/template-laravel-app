# Designing for performance

This page is about the model: which access paths the schema must serve, what makes a shape
indexable at all, and what a row's growth does to it. What index type serves a path, and what a
planner does with it, belongs to the engine package you are running.

Design-time performance is not tuning. Tuning changes the plan for a query the schema already
supports; this page is about not building a shape that no plan can rescue.

## Start from the access paths, not the entities

List the queries the schema must serve before drawing tables: the predicate columns, the sort, the
expected result size, and how often each runs. A model that is correct in the abstract can still make
its most frequent query unanswerable without a scan.

For each path, record the selectivity of the predicate and the cardinality of the result. A filter
that matches most rows is not helped by an index at all, and designing around one is wasted effort.

## Make the shape indexable

Some shapes cannot be indexed no matter which engine runs them. These are modelling defects, not
tuning problems:

- **A repeating group in a column.** `tags TEXT -- "a,b,c"` cannot be filtered, constrained, or
  joined through. The junction table is the fix, and it is a modelling change.
- **A value hidden inside a wrapped expression.** If every query filters on a transformation of the
  column, the plain column is the wrong column. Store what you filter on.
- **A predicate spread across two columns that always travel together.** If the pair is always
  queried together, it is one composite key in the model, and its column order follows the access
  path — equality first, then the range or sort.
- **A polymorphic reference with no constrained target.** A `commentable_type` / `commentable_id`
  pair cannot carry a foreign key, so integrity moves into application code and the join cannot be
  planned as one. `advanced-patterns.md` covers the alternatives; the cost here is that the shape
  forecloses the engine's help.

## Choose keys for what they do to every other structure

A primary key is copied into the structures that reference it, so its width and its ordering are
model-wide decisions, not table-local ones:

- A wide key multiplies across every referencing index and foreign key.
- A key with no natural order scatters inserts instead of appending them, which costs write
  throughput and locality on any engine that stores rows in key order.
- A key generated by the application can be assigned before the row exists, which a
  database-generated one cannot. That is a modelling property, and sometimes the deciding one.

Where a random identifier is required externally, keep it as a separate unique column and let the
internal key stay narrow and ordered. The engine packages state what each engine does with this;
the decision to separate the two is the model's.

## Let time and volume into the design

Ask what the largest table looks like after two years of the real arrival rate, and which queries
still touch the whole thing.

- A table that only ever grows needs a bounded read path: keyset pagination rather than large
  offsets, and a predicate on a monotonic column rather than a scan and sort.
- Data with a retention rule should be modelled so that expiring it is a bounded operation rather
  than an unbounded delete.
- If a table is destined for partitioning, the partition key constrains the primary key from the
  first migration onward. Retrofitting it is a rebuild, which is why it is a design decision and not
  an operational one.

## Separate the read shape from the write shape deliberately

Normalize for writes; when reads genuinely need a different shape, add the second shape explicitly
and own its staleness.

```sql
-- Bad: a counter kept on the parent with nothing keeping it true.
ALTER TABLE posts ADD COLUMN comment_count INTEGER NOT NULL DEFAULT 0;

-- Good: the derived value is declared as derived, and the refresh path is named.
CREATE TABLE post_comment_counts (
  post_id        INTEGER PRIMARY KEY REFERENCES posts(id) ON DELETE CASCADE,
  comment_count  INTEGER NOT NULL,
  counted_at     TEXT    NOT NULL
);
```

The bad version is not wrong because a counter is wrong — it is wrong because nothing in the schema
says the column is derived, so a future writer will treat it as a fact and the two sources of truth
will diverge silently. The good version makes the derivation and its freshness visible, and the
refresh becomes something you can test.

Do this from a measurement. A duplicated value is a second source of truth and the code that
maintains it can be wrong, so it must buy a cost you have actually observed — a profiled query, not
an anticipated one.

## Prove the shape before committing to it

A schema decision is verifiable before the application exists:

1. Load representative volume, not ten rows. Plans change with cardinality, and a shape that scans
   happily at a thousand rows is the one that fails at a million.
2. Run the access paths you listed and read the plans. Confirm the frequent ones use the structures
   the model implies.
3. Record the numbers with the row counts they were measured at. A timing with no volume attached
   proves nothing about the shape.

If a measurement is not available yet, say so and state the assumption the shape rests on rather
than presenting a prediction as evidence.
