# Migrating a fork to template v4.5.0

This guide walks an agent (or human) through applying v4.5.0 to a fork that is currently at v4.4.0. Every step has a verification command — do not bump `template-version.json` until every checkbox is verified and `pnpm check` is green.

## Overview

v4.5.0 is a **scaffold correctness pass** plus one infrastructure improvement. It fixes bugs in the shared scaffolding the template ships (data-table state, real-time/SSR plumbing, shadcn-vue components, base service, auth middleware, tooling), and moves Ziggy generation to the build pipeline so `route()` produces real URLs in both browser and SSR. Most fixes are drop-in. One behavior change — `Route::get('logout', ...)` → `Route::post('logout', ...)` — requires a fork-side frontend audit.

## Prerequisites

- Fork's `template-version.json` is currently at `4.4.0` (or earlier — apply prior migrations first).
- Tests pass on baseline: `pnpm check` is green.
- You have read-write access to the fork repo.

## Apply order

Work top-down, one group at a time, and run `pnpm check` (or at least the most relevant subset) after each group. If a fix already exists in the fork (one of the forks contributed it back), the verification command will still pass — no harm done.

### Group A — Data-table state isolation

- [ ] Replace `resources/js/composables/inertia/useDataTableOptions.js` with the v4.5.0 version (copy from template).

  ```bash
  grep -n 'unsubscribe' resources/js/composables/inertia/useDataTableOptions.js
  ```
  → must report at least one match (the captured `router.on('before', ...)` return).

  ```bash
  grep -n 'SSR_SAFE_URL_BASE' resources/js/composables/inertia/useDataTableOptions.js
  ```
  → must report a match.

### Group C — Real-time / SSR plumbing

- [ ] Patch `resources/js/composables/useEcho.js` (drop `'private-' + ` and `'presence-' + ` prefixes from `echo.leave(...)` calls; add `channel.stopListening` to `useListen` cleanup).

  Verify (must return **no matches**):
  ```bash
  grep -nF "echo.leave(\`private-" resources/js/composables/useEcho.js
  grep -nF "echo.leave(\`presence-" resources/js/composables/useEcho.js
  ```
  (`-F` switches grep to fixed-string mode so the parens/backtick are literal.)

  Verify (must match):
  ```bash
  grep -n 'channel.stopListening' resources/js/composables/useEcho.js
  ```

- [ ] Patch `resources/js/bootstrap.js` (add axios `X-Socket-Id` interceptor).

  Verify:
  ```bash
  grep -n 'X-Socket-Id' resources/js/bootstrap.js
  ```
  → must match.

- [ ] **Move Ziggy to the build pipeline.** This replaces the old "no-op SSR fallback" approach with full Ziggy library resolution in both browser and SSR. After this group, `route()` returns real URLs everywhere.

  1. Add `qs-esm` to JS deps: `pnpm add qs-esm` (or `pnpm add qs-esm@^8.0.1` for pinning).
  2. Add to `.gitignore`:
     ```
     # Ziggy — generated by `php artisan ziggy:generate` on `composer install`,
     # `pnpm dev`, and `pnpm build`. Never author-edited.
     /resources/js/ziggy.js
     /resources/js/ziggy.d.ts
     ```
  3. If a generated `resources/js/ziggy.js` is currently committed in the fork, untrack it: `git rm --cached resources/js/ziggy.js`. (Don't physically delete — `pnpm dev` will regenerate.)
  4. In `composer.json`, append `"@php artisan ziggy:generate --ansi"` to the `post-autoload-dump` array.
  5. In `package.json`, prepend `php artisan ziggy:generate &&` to `dev`, `build`, and `build-ssr` script values.
  6. Replace `resources/js/plugins/inertia/ziggy.js` with the v4.5.0 version (uses `import { route as ziggyRoute } from 'ziggy'` and wires globalThis/inject/$route to `(name, params, absolute=false, config) => ziggyRoute(name, params, absolute, config ?? globalThis.Ziggy)`).
  7. In `resources/js/setup.js`, add at the top (after existing imports):
     ```js
     import { Ziggy } from './ziggy';
     globalThis.Ziggy = Ziggy;
     ```
  8. Run `php artisan ziggy:generate` once manually, then `pnpm build-ssr` to confirm both bundles produce.

  Verify:
  ```bash
  grep -n 'ziggy.js' .gitignore
  grep -nF '@php artisan ziggy:generate' composer.json
  grep -nF 'php artisan ziggy:generate' package.json
  grep -n "from 'ziggy'" resources/js/plugins/inertia/ziggy.js
  grep -n "globalThis.Ziggy = Ziggy" resources/js/setup.js
  ```
  → all five must match.

- [ ] **Fork-side audit:** find all logout call sites in the fork's frontend and confirm each one uses POST.

  Find:
  ```bash
  grep -rn 'logout' resources/js/components resources/js/pages 2>/dev/null | grep -vE 'useForm|method:.*post|method="post"'
  ```
  Review each match. Anything that looks like `<a href="/logout">` or `<Link href="/logout">` (without `method="post"` / `as="button"`) must be converted to one of:
  - Inertia `<Link>` POST: `<Link as="button" method="post" :href="$route('auth.logout')">Logout</Link>`
  - A form: `<form :action="$route('auth.logout')" method="POST"> @csrf <button>Logout</button> </form>`
  - `useForm()`: `const form = useForm({}); form.post(route('auth.logout'))`

  In the template, the canonical way for `ProfileMenu` items is to pass `method: 'post'` on the menu item config — `ProfileMenu.vue` will then render the `<Link>` as a button-style POST. Replicate that pattern in any fork that customized `ProfileMenu`.

## Finalize

- [ ] Run `pnpm check`. All checks must pass.

  ```bash
  export PATH="$HOME/Library/Application Support/Herd/bin:$PATH"
  pnpm check
  ```

- [ ] Smoke-test the app:
  - Login → admin → users list (data-table).
  - Open a row's selection, navigate to a different admin section → selection should NOT leak.
  - Toggle dark mode → hard-reload → confirm no FOUC flash on first paint.
  - Log out → confirm the POST endpoint accepts and redirects correctly.
  - View source on `/login` → confirm `<html lang="en">` is present.

- [ ] Bump `template-version.json`: `version` → `"4.5.0"`, `updated` → today's ISO date.

- [ ] If the fork keeps its own customer-facing `CHANGELOG.md`, copy the v4.5.0 entry from the template's `CHANGELOG.md` into the fork's release log (or note "template baseline → v4.5.0" if the fork's changelog uses product semver and tracks template lineage separately — e.g. rundesk-web-app).

Most Group C, E, F, G, H checks will already pass. Verify each file matches the v4.5.0 canonical version, then bump.
- **`aprillaneart-site`** already ships its own version of: `useDataTableOptions.js`, `eslint.config.js` (ziggy ignore), `package.json` (pest memory bump), `DropdownMenuItem.vue`, `AccordionContent.vue`, `AccordionItem.vue`, `DialogConfirmation.vue`, `Login.vue` / `Register.vue` (`$route()`), `app.blade.php` (`lang="en"`). Most Group A, D, F, G checks will already pass. Verify each file matches the v4.5.0 canonical version, then bump.

For both forks, the `ModelService.php` reconciliation needs care: `applySearch`/`applyWith` came from aprillaneart; the `listPaginated` tiebreaker + page override came from rundesk. The v4.5.0 canonical file has both. When you bump rundesk, make sure the `applySearch`/`applyWith` helpers get added. When you bump aprillaneart, make sure the `orderBy('id','asc')` tiebreaker + `$page` override land. Diff against template after editing to confirm.

## When to bump `template-version.json`

Only after **every** checkbox above has passed AND `pnpm check` is green. Setting the version ahead of the actual state breaks the "highest fully-applied" contract that workspace tracking relies on.

## Rollback

If `pnpm check` fails after a group:

1. `git status` to see what changed.
2. `git diff` to inspect the failing area.
3. Re-read the v4.5.0 source in the template repo for the file in question.
4. Fix the divergence. (Do not partial-bump — either the whole release is applied or it isn't.)

If you cannot resolve the failure: `git checkout -- <file>` to drop the change, ask the human, and leave `template-version.json` at `4.4.0`.
